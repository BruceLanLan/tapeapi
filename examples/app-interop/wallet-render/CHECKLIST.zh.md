# 钱包显示实测清单（访客授权 v1）

> **实验性原型，不是 TAP，不发送任何交易。** 本清单配合同目录的本地测试页使用：用三个**新建的空钱包**（MetaMask、OKX Wallet、Rabby）各对访客授权 v1 的 EIP-712 类型数据签一次，看钱包怎样显示它。不花 gas、不上链、不联网请求任何服务；签出的东西不被任何服务接受。页面里的 12.7.tape、13.7.tape 是示例名字，不是真实服务；地址都是重复字节的夹具。

预计用时：**1–1.5 小时**（准备 30 分钟，每个钱包 15–20 分钟，整理 10 分钟）。

---

## 1. 准备（约 30 分钟）

1. **三个独立的浏览器用户资料**（Chrome 或 Brave 的"新建个人资料"），每个资料只装**一个**钱包扩展。同一个资料里装多个钱包，它们会抢 `window.ethereum`，记录就分不清是谁在答。
2. 从各自的**官方扩展商店**安装：MetaMask、OKX Wallet、Rabby。记下各自的版本号（扩展管理页可见）。
3. 每个钱包都**新建**钱包（新助记词）。**不要导入任何已有钱包，不要往里转任何资产。** 助记词只为这次测试，测完可以连扩展一起删掉。
4. 把网络切到 **BNB Smart Chain（链 ID 56）**：
   - MetaMask：网络列表 →"添加网络"里的 BNB Chain（热门网络，内置），或手动添加链 ID 56；切过去。
   - OKX Wallet、Rabby：默认支持 BNB Chain，在钱包里选中它即可。
   - 原因：类型数据的域写的是链 ID 56，钱包当前网络不一致时多半会拒签（这本身也值得截图记录）。
5. 准备一个存档文件夹，例如 `wallet-render-results/`（放截图与结果 JSON，**不要放进仓库**）。

## 2. 启动测试页

在仓库根目录：

```bash
node examples/app-interop/wallet-render/serve.mjs          # 默认端口 8787；只监听 127.0.0.1
# 浏览器打开 http://localhost:8787/
```

备选（没有 Node 时）：`python3 -m http.server 8787 --bind 127.0.0.1 --directory examples/app-interop/wallet-render`，同样打开 `http://localhost:8787/`。

可选的自查：打开开发者工具的"网络"面板再刷新，应当只有 `localhost` 上的三个文件（`/`、`app.js`、`payloads.js`），之后点任何按钮都不应出现新的网络请求。

**任何时候钱包弹出的是"发送交易"、"授权代币（approve）"、"切换网络"、"添加网络"或要求输入助记词——立即拒绝，截图，停下来回报。** 本页不会发起这些请求。


## 5. 判定标准

**过**（全部满足）：

1. **至少两个**钱包（MetaMask、OKX Wallet、Rabby 中任两个）在 BNB Smart Chain（链 ID 56）下弹出了签名请求并完成签名，`check-result` 为 OK，截图可读。
2. 对 v1-en 与 v1-en-max：`statement` 的**第一行在首屏完整显示**，或者钱包提供了明显的展开方式能看到全文（记录首屏可见字符数）。
3. `string[] methods` **逐项可见**（8 项的情形也要能看到全部，可以滚动）。
4. `callerName` 与 `caller`、`audienceName` 与 `audience` **成对可见**（相邻或同屏）。
5. 域四项（name、version、chainId、verifyingContract）可见；`verifyingContract` **没有安全警告**，或者警告原文已经截图记录。
6. 记录了每个钱包"请求来自"显示的来源字符串。

**不过**（任一出现）：

- 第一行被截断**且不能展开**看到全文；
- `methods` 只显示"数组 / 3 items"之类而看不到内容，且不能展开；
- 两个以上钱包拒签或不显示类型数据（只显示一串十六进制）。

`verifyingContract` 被标红或拦截**不单独判不过**：记录原文，交给决定域与 `verifyingContract` 的人。

## 6. 失败或异常时怎么回报

交回这三样：**记录表**、**全部截图**、**全部结果 JSON**（含失败的）。另写几行：

- 哪个钱包、哪个版本、哪份数据、第几步；
- 钱包原话（错误或警告的原文，不要意译）；
- 是否重复出现（刷新页面、重启浏览器后再试一次的结果）。

不要做的：不要改页面去"让它过"；不要换成有资产的钱包重试；不要点任何交易、授权代币或切换网络的请求。

## 附：如果第一行被截断了，我们怎么办（只列思路，不改向量）

这些都是**格式改动**，要在实测结论出来、并由决定格式的人同意之后才做；做的时候一律**升 `v`（v2）**，v1 原样不动，重新生成向量并用三种实现（JS、`verify.py`、Solidity）复算一致。现在一项都不做。

1. **缩短第一行**：v2 模板把第一句压到实测"首屏可见字符数"的最小值以内，只放最要紧的一件事——"允许 〈A 的名字〉 代表我调用 〈B 的名字〉"；方法、次数、起止时间、"不含任何付款"、撤销方式移到第二句及以后。
2. **把要核对的名字放在最前**：第一句以调用方名字开头（访客唯一要核对的就是它与"请求来自"是否一致）。
3. **拆字段**：把一段长 `statement` 拆成几个短的字符串字段（例如"谁 / 做什么 / 多久"），每个字段各自一行显示；代价是字段名也会被显示，且服务端逐字重建的规则要跟着改。
4. **字段顺序**：`callerName` 紧跟第一行，`audienceName` 紧随其后，地址字段放在名字后面，让"名字与地址成对"在首屏出现。
5. **数组太长**：若 8 项方法不能逐项显示，v2 把方法上限从 8 降到 4，或把方法名长度上限从 64 降到 32；或者第一行里只写方法个数，方法清单留在数组里。
6. **域显示**：若域名被截断，考虑更短的域名（域名本身是待定项）；若 `verifyingContract` 被标红，记录钱包原话，交给决定"用 hub 还是用被调用方的容器"的人。
7. **钱包只显示十六进制**：说明该钱包不解析这份类型数据；记录下来，不为它改格式（改了也解决不了），在文档里写明该钱包下访客无法核对。

每条改动都要回到本清单再测一遍，才能谈"过"。
