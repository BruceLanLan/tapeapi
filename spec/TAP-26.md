# TAP-26: Tape Channel: Real-Time Private Channels Between Containers

> English is authoritative. 中文译文见下半部分，章节编号一一对应。

> **Placeholder number.** TAP-26 is a placeholder number proposed in [TapeKit issue #8](https://github.com/TapeOutProtocol/TapeKit/issues/8). TapeKit has no numbered-proposal process yet (changes to TapeOut itself follow TapeKit `SPEC.md` §15), so the maintainers may assign another number or move this document to another process; see [TAP-1](TAP-1.md).

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in RFC 2119.

## 1. Abstract

A Tape Channel is an end-to-end encrypted, mutually authenticated, ordered stream of messages between two TapeOut containers. It is set up with one invite -- posted to the peer's inbox room on a relay or ChannelBus (the default), or sent as a TapeSend message (the durable fallback) -- and then runs over any transport: a relay that is itself a TapeAPI service (the default: fast, free per frame, no permanent record), a direct browser connection, or — when no relay is wanted or available — the chain itself through a ChannelBus (§3.7). Each party is identified by channel keys its circuit's holder authorised and published in the container's own DeWEB site, so a channel needs no new contract, no trusted server, and no signature on another site's text.

## 2. Motivation

DeWEB serves sites and TapeSend carries messages between people, but TapeSend writes every message to the chain: it costs gas, it takes a block, and who talked to whom is public. Nothing in the ecosystem supports the conversations that need to happen many times a second between two parties who must not be overheard, and that is why every TapeOut game so far is single-player. A card game with hidden hands, a negotiation, a live collaborative document, a service streaming results to one client -- all need a channel that is private, fast and cheap per message, while still being bound to the on-chain identities the rest of the ecosystem trusts.

TAP-26 supplies that channel and deliberately nothing else. It says nothing about games, state machines or settlement; applications build those on top.

## 3. Specification

### 3.1 Identities and keys

- Each party is a TapeSend endpoint: `uint32(0) ‖ uint64(chainId) ‖ container` (32 bytes, exactly as TAP-10 builds it).
- **Channel identity (default).** A container's identity for this TAP is a pair of keys generated by the application and kept by it: an X25519 key (the **static key** of the handshake) and an Ed25519 key (used by TAP-27 group messages). The circuit's holder authorises them with an EIP-712 signature in the TAP-20 domain (`name "TapeAPI"`, `version "1"`, `chainId`, `verifyingContract` = the DeWebHub) over

  ```
  ChannelKeys(address container,bytes32 x25519,bytes32 ed25519,bytes32 inbox,uint64 issued,uint64 expires)
  inbox = keccak256(UTF-8(canonicalJSON({ "relays": [ { "url", "container" } ], "bus"? })))
  ```

  and publishes a record in the container's DeWEB site at registry key `.well-known/tape-channel.json`:

  ```json
  { "tapechannel": "1", "container": "0x…", "chainId": 56, "x25519": "0x<64 hex>", "ed25519": "0x<64 hex>",
    "issued": <unix seconds>, "expires": <unix seconds>, "sig": "0x<130 to 2048 hex>",
    "inbox": { "relays": [ { "url": "https://…/tapeapi/v1", "container": "0x…" } ], "bus": "0x…" } }
  ```

  `inbox` in the signed struct is the hash of the record's `inbox`, normalised: `relays` always present (each entry reduced to `url` and `container`; `[]` when absent), `bus` only when present. The holder's signature therefore covers where invites go, and whoever can write the site cannot redirect them. `sig` is 65 bytes (`r ‖ s ‖ v`) for an ECDSA holder, or up to 1,024 bytes for a contract holder (EIP-1271). The type name differs from the TAP-20 `Delegation`, so a service delegation can never be replayed as a channel authorisation. No wallet signature is ever turned into a key: the holder signs structured data that states what it authorises, and nothing asks the holder to sign text intended for another site.
- **Reading it.** Given a container, call its ERC-6551 `token()` to obtain `(chainId, circuits, tokenId)`; `chainId` MUST equal the chain being read, `DeWebHub.accountOf(circuits, tokenId)` MUST equal the container, and the processor factory MUST answer `isCPU(circuits) == true` (the same checks as TAP-20 §3.6: a container's own `token()` is only a claim, and `accountOf` derives an account for any ERC-721, counterfeit ones included). Read the record with `SiteRegistry.read` and verify its bytes against `fileInfo` exactly as TAP-20 §3.2 does for a manifest (at most 4,096 bytes). The record MUST parse under the strict rules of TAP-21 §3.3; `container` and `chainId` MUST match; `x25519` MUST pass the checks below; `ed25519` MUST pass the Ed25519 check below; `issued` MUST be an integer no more than 300 s ahead of the reader's clock and below `expires`; `expires` MUST be in the future and at most 366 days ahead (a MUST here, where TAP-20 §3.4 has a SHOULD: a channel identity must lapse); `inbox` entries MUST satisfy §3.2 step 1. Finally the signature MUST recover to `ownerOf(circuits, tokenId)` read now, or, when that owner is a contract, the owner MUST accept it under EIP-1271: `isValidSignature(digest, sig)` MUST return the full 32-byte word `0x1626ba7e` followed by zeros. A circuit that changes hands therefore drops its channel identity by itself. Every read uses the quorum rules of TAP-20 §3.2. A holder withdraws the identity early by removing the file. A client MUST remember, per container, the highest `issued` of a record it accepted, and MUST refuse a record with a lower `issued` (it SHOULD persist this floor): a holder's signature does not expire when the holder replaces the record, so without the floor anyone able to write the site could put a replaced record, and a leaked key, back. A holder replacing a record MUST give the new one a higher `issued`.
- **TapeSend keys (fallback).** A party MAY instead authenticate with the X25519 key TAP-10 §4 derives from the holder's wallet and publishes on the DeWebHub, read with `DeWebHub.keyFor(circuits, tokenId)` (the returned `container` and `endpoint` MUST match, `usable` MUST be true, `suite` MUST be 1). That derivation asks the holder to sign text stating it should be signed only on the TapeSend site, so an implementation other than the official TapeSend client SHOULD NOT ask for it. On 2026-09-22 `keyFor` for container `0x86DDaEF00401E3F10418398D67D7189fc458eA95` returned a usable suite-1 key (raw responses in `sdk/test/fixtures/mainnet-4246-tapesend-key.json`).
- The invite states which kind both parties use (`keys`: `"tape-channel/v1"` or `"tapesend/v1"`, §3.2), and the transcript binds it. A client MUST NOT take a peer's static key from any message of this TAP.
- Every public key a client receives, static or ephemeral, MUST be 32 bytes, have its top bit clear, be canonical (`u < 2^255 − 19`), and MUST NOT yield an all-zero X25519 shared secret (TAP-10 §4.4). A key failing any of these MUST cause the handshake to be abandoned.
- Every Ed25519 public key MUST decode to a point on Ed25519 and MUST NOT be a small-order point: a small-order key lets one signature verify for every message.

### 3.2 Handshake

Three messages. A is the initiator, B the responder. Roles are fixed by who sent the invite.

1. **Invite** (A → B). A draws a random 16-byte channel id `cid` and an ephemeral X25519 key pair `(eA, EA)`, and builds:

   ```json
   { "v": 1, "kind": "tape.channel/invite", "cid": "<32 hex>", "e": "<64 hex: EA>", "exp": <unix seconds>,
     "from": { "container": "0x…", "chainId": 56 }, "keys": "tape-channel/v1",
     "relays": [ { "url": "https://…/tapeapi/v1", "container": "0x…" } ], "bus": "0x…", "webrtc": { … } }
   ```

   `from` and `keys` are REQUIRED. `from` names the initiator and `keys` the kind of static keys both parties use (§3.1); B MUST look A's static key up from `from` by the kind `keys` names, and MUST refuse an invite whose `from` is not the party whose key it looked up. Nothing in the invite is trusted for identity: a forged `from` or `keys` changes `inviteHash`, and the handshake then fails (§3.3).

   **Delivery.** The invite reaches B by either path; both are safe because the handshake, not the path, authenticates it:

   - **Inbox room (default).** Every container has an inbox room `SHA-256("TAP-26/inbox/v1" ‖ endpoint)` on any relay (§3.5) or ChannelBus (§3.7) that its record lists under `inbox`. A posts there the wire message `0x03 ‖ E ‖ N ‖ C`: `e` a fresh X25519 secret, `E = X25519(e, 9)`, `N` 24 random bytes, `K = HKDF-SHA256(X25519(e, R), salt = "TAP-26/inbox/v1", info = E ‖ R ‖ room, L = 32)` with `R` B's static key, and `C = XChaCha20-Poly1305(K, N, aad = "TAP-26/inbox/v1" ‖ E ‖ room).encrypt(UTF-8(canonicalJSON(invite)))`, where `room` is the 32 raw bytes of the room id. The whole wire message is at most 16,448 bytes. Wire type `0x03` carries any strict-JSON object with `v` 1 and a string `kind`, and the receiver dispatches on `kind`: TAP-26 invites (`tape.channel/invite`) and TAP-27 group invites (`tape.group/invite`) share it, and one cannot be taken for the other. Anyone can post it; no holder transaction is needed. Only the room (which identifies B) and the size are visible.
   - **TapeSend (durable fallback).** A's holder sends a TapeSend message (TAP-10 §5.3) whose content is the invite, sealed to B's static key. It reaches a peer that is offline for longer than a relay or node keeps data, at the cost of one holder transaction. B MUST check that the TapeSend `from` equals `invite.from`.

   A TAP-10 client that does not implement this TAP decodes the content as an unsupported kind (TAP-10 §6) and MUST NOT act on it; no change to TAP-10 is required.

   `exp` MUST be at most 3600 seconds after the time of sending (RECOMMENDED 600). `relays` lists at most 4 TapeAPI relay services (§3.5) on which A will listen; each `url` MUST be an `https` URL of at most 512 characters (plain `http` only for a loopback host during development, as for any TAP-20 endpoint), and `container` MUST be the relay's TAP-20 identity (a 20-byte hex address). A client resolves the relay by that container (TAP-20 §3.6) to learn its signer, its prices and its current endpoints; a URL alone carries none of that, so an invite that omits the container cannot be acted on. `bus` is OPTIONAL: the address of a ChannelBus on which A also listens (§3.7). An invite SHOULD list at least one relay or a bus; an invite with neither can only be answered out of band. `webrtc` is OPTIONAL (§3.6); if present it MUST have a canonical form (TAP-21 §3.3), since the whole invite is hashed into the transcript (§3.3). `cid` is emitted as 32 lowercase hex characters; receivers MUST compare channel ids as bytes, not as strings.

2. **Accept** (B → A, posted to A's inbound room on a relay or ChannelBus the invite names). `exp` is exclusive for the invite: B MUST reject it unless `now < exp ≤ now + 3600`, MUST validate `EA` per §3.1 and `relays` per step 1, and SHOULD refuse a `cid` it has already accepted (remembering accepted ids until their `exp` is the application's job; the reference SDK takes a caller-supplied set). B draws `(eB, EB)`, derives the keys (§3.3) and sends `{ "t": "accept", "cid": "<hex>", "e": "<hex: EB>", "confirm": "<hex: confirmResponder>" }`. B MUST erase `eB` once the keys are derived.

3. **Ready** (A → B, on the same transports). A MUST verify `accept.confirm` in constant time before sending anything, and accepts an `accept` only while `now < exp`. An `accept` that does not verify MUST be discarded and MUST NOT create a session; A keeps waiting for a valid `accept` until `exp` (anyone who reads A's relay room can post a bogus one, so treating it as fatal would hand every relay observer a kill switch). After a valid `accept`, A sends `{ "t": "ready", "cid": "<hex>", "confirm": "<hex: confirmInitiator>" }` and MUST erase `eA`; a second `accept` for the same handshake MUST NOT complete it again. B MUST verify `ready.confirm` in constant time, MUST refuse a `ready` unless `now < exp` (the same exclusive bound as the invite), and MUST NOT accept any inbound frame until it has verified one.

A's pending handshake state (`eA` and everything derived from it) MUST NOT be persisted or copied: completing the same handshake twice derives the same keys and restarts `seq` at 0, which reuses nonces. A handshake whose state is lost is restarted with a new invite.

B MAY send frames immediately after `accept`: only a party holding both `sA` and `eA` can read them.

### 3.3 Key schedule

```
inviteHash = SHA-256( UTF-8( canonicalJSON(invite) ) )             -- the whole invite content of §3.2 step 1, TAP-21 §3.3
transcript = SHA-256( "TAP-26/transcript/v1" ‖ cid ‖ endpointA ‖ endpointB ‖ SA ‖ SB ‖ EA ‖ EB ‖ uint64be(exp) ‖ inviteHash )
ikm        = DH(eA, SB) ‖ DH(sA, EB) ‖ DH(eA, EB)                 -- each 32 bytes; B computes the same three
okm        = HKDF-SHA256(ikm, salt = transcript, info = "TAP-26/keys/v1", L = 128)
kAB ‖ kBA ‖ cA ‖ cB = okm                                            -- 32 bytes each
confirmInitiator = HMAC-SHA256(cA, "TAP-26/confirm/initiator" ‖ transcript)
confirmResponder = HMAC-SHA256(cB, "TAP-26/confirm/responder" ‖ transcript)
```

`kAB` protects frames from A to B, `kBA` frames from B to A. The two MUST NOT be used for the other direction. Implementations SHOULD erase `ikm`, `okm`, `cA`, `cB` and the three DH outputs once the confirmation tags are computed.

`inviteHash` binds everything the invite carried, including `relays` and `webrtc`, so an invite altered in transit (a swapped relay list, a changed `exp`) yields confirmation tags that do not verify.

### 3.4 Frames

```
frame = uint64be(seq) ‖ ChaCha20-Poly1305(key, nonce = 0x00000000 ‖ uint64be(seq), aad, plaintext)
aad   = "TAP-26/frame/v1" ‖ cid ‖ dir ‖ uint64be(seq)            -- dir = 0x00 for A→B, 0x01 for B→A
```

- Each direction keeps its own `seq`, starting at 0 and incremented by one per frame. A sender MUST NOT reuse a `seq` and MUST open a new channel before `seq` reaches 2^32.
- Plaintext MUST NOT exceed 16,384 bytes per frame.
- A receiver MUST reject a frame whose `seq` is not greater than the highest `seq` it has accepted in that direction (replayed, duplicated or reordered), and MUST reject a frame that fails authentication. A receiver MUST accept a gap and SHOULD report its size to the application: transports may lose frames, and whether a loss is tolerable is an application decision.
- A receiver that decodes plaintext as text MUST do so before advancing its highest accepted `seq`, and MUST reject an authentic frame that is not valid UTF-8 without consuming it.
- The channel's confidentiality, integrity and ordering MUST NOT depend on the transport.

### 3.5 Relay profile

A relay is a TAP-20/21 service whose manifest lists three methods:

| Method | Price | Params | Result |
|---|---|---|---|
| `relaySend` | set by the operator, MAY be 0 (TAP-22 per call) | `{ room, frame }` | `{ i, epoch }` |
| `relayHandshake` | MUST be 0 | `{ room, frame }` | `{ i, epoch }` |
| `relayRecv` | 0 | `{ room, after, waitMs, epoch? }` | `{ frames: [{ i, frame }], next, epoch }` |

- `room` is `SHA-256("TAP-26/room/v1" ‖ cid ‖ dir)` as lowercase hex, with `dir = 0x00` for messages **to** the initiator and `0x01` for messages **to** the responder. Only parties who read the invite know `cid`, so a channel room name is an unguessable capability that reveals no identity. Inbox rooms (§3.2) are not: anyone can derive a container's inbox room and post to it.
- `frame` is standard padded base64 of one **wire message**: `0x01 ‖ UTF-8 JSON` for `accept` or `ready`, `0x02 ‖ frame` (§3.4), or `0x03 ‖ sealed invite` posted to an inbox room (§3.2). A relay caps the size of a frame (the reference relay: 22,000 base64 characters, which holds the largest wire message, 16,448 bytes).
- `i` is the relay's own index within the room, strictly increasing. `relayRecv` returns the stored frames with `i > after` (a client's first `after` is −1), and if there is none MAY hold the request for up to `waitMs` and answer as soon as one arrives. A relay caps `waitMs` below its own response deadline (the reference relay: 20,000 ms, under the reference server's 25,000 ms handler timeout), or a full-length poll is answered with `INTERNAL` instead of an empty result.
- **An answer MUST fit the TAP-21 response cap (1 MiB).** A relay returns as many frames as fit under a byte budget (the reference relay: 512 KiB), always at least one, and `next` says where to continue; the client polls again immediately. A relay that instead returned its whole backlog would, once a room held enough full frames, fail every poll: the cursor would never advance and the channel would be dead for good — which anyone who learned the room id could trigger for free.
- **A priced relay MUST carry the handshake for free** through `relayHandshake`. Its `frame` is small (the reference relay: at most 2,048 base64 characters) and MUST decode to `0x01` followed by a JSON object whose `t` is `accept` or `ready`; the relay refuses anything else. A relay MAY refuse more than N such messages per room (the reference relay: 8). Rooms the free path creates have their own cap (the reference: 1,000) and a shorter lifetime (the reference: 10 minutes) until a paid `relaySend` adopts them, so the free path cannot fill a priced relay's room table. The responder has to answer an invite before it has any reason to have funded a channel toward that relay, and `accept` is what tells the initiator the channel exists; paying for it would require three on-chain transactions inside the invite's lifetime.
- `next` is the value to pass as `after` in the following call: the last returned `i`; `after` unchanged when nothing was returned; or −1 when the room's `epoch` changed and nothing was returned.
- **Epoch.** A relay MUST give each room a random `epoch` (RECOMMENDED 8 bytes, hex; it MUST match `^[0-9a-f]{1,32}$`) when the room is created, and return it from every method (`null` from `relayRecv` for a room that does not exist). Indices restart in a re-created room (a relay restart, an expired room, a new Durable Object), so a client MUST send the `epoch` it last saw with `after` (`null` if the room did not exist or the client has not polled it yet; a relay MUST accept it, and it differs from every epoch); when the relay's `epoch` differs it MUST answer as if `after` were −1, and the client MUST reset its cursor. A relay SHOULD also accept a request with no `epoch` field, which reference clients before 2026-09-27 sent before they had seen one, and answer it from `after` as given. Without this, a client that remembered index N silently skips the first N+1 frames of the new room.
- **Rooms.** Only a post (`relaySend` or `relayHandshake`) creates a room; a `relayRecv` on a room that does not exist waits without creating or pinning it, and a relay SHOULD bound the number of waiting requests separately. A relay SHOULD bound frames per room, room lifetime and the number of rooms, and SHOULD keep an idle room for at least 600 s (the RECOMMENDED invite lifetime) so that an `accept` posted while the initiator is briefly offline is still there; and MAY drop a room's oldest frames (the receiver sees the gap). A relay MUST NOT evict a room that has not expired in order to make room for a new one; when full it refuses the new room (`INTERNAL`, or HTTP 503 at the edge), because evicting live rooms would let anyone flush other channels' undelivered frames.
- **Several transports.** The initiator MUST listen for `accept` on every relay and every ChannelBus the invite names, from the moment it sends the invite until `exp`. The responder SHOULD post `accept` to the first of them it can reach, in the order the invite lists them (relays, then the bus), and MAY post it to all of them. A receiver MUST treat identical wire messages that arrive on several transports as one. `ready` and later frames SHOULD go on the transport the `accept` arrived on. The reference `fanIn` joins several transports into one.
- **Invites and epoch messages are kept apart.** A relay MUST hold wire types `0x03` (sealed invite) and `0x04` (group epoch message) under a bound of their own that frames (`0x02`, `0x05`) cannot evict (the reference relay: 64 per room, oldest first), so that a flood of frames, free on a free relay, cannot flush a peer's inbox or a group's current epoch before it is read. Within a room `relayRecv` MUST still return messages of every type in posting order under one index sequence. A relay SHOULD cap `0x03` and `0x04` posts per room per source (the reference: 8 per 10 minutes, keyed by the paying consumer, else by the caller's address; a caller it cannot identify counts as one source for the whole room) and refuse further ones as a caller error (`BAD_REQUEST`).
- A client MUST decode each returned frame independently: a malformed frame is reported and skipped, never allowed to discard the frames after it.
- A relay MUST NOT be trusted for content, ordering or completeness: clients rely on §3.4 for all three.
- Because every `relayRecv` answer is a TAP-21 envelope, a relay's claim to have delivered or not delivered a frame is signed.

### 3.6 Direct transport (OPTIONAL)

Parties MAY move a channel onto a WebRTC data channel. The SDP offer MAY travel in the invite (`webrtc.sdp`) and the answer in `accept`. Frames on the direct transport are the same frames with the same keys and the same `seq` counters, so a channel can switch between relay and direct in either direction without renegotiation, and a receiver simply applies §3.4 to whatever arrives.

Whether a DeWEB page may open a WebRTC connection at all is a shell decision outside this TAP (TapeKit SPEC §7 governs off-chain requests and does not currently address WebRTC). Relay transport MUST be supported by every implementation; direct transport is an optimisation.

### 3.7 On-chain transport (OPTIONAL)

The chain itself can carry a channel, with no relay and no operator. A **ChannelBus** is a contract with this interface (reference: `contracts/src/ChannelBus.sol`; deployed on BNB Chain at `0x486110c35d9b90a9d6D85c8063A065f9e7b6b707`, whose code is byte-for-byte the reference build; any contract with this interface serves equally):

```solidity
function send(bytes32 room, bytes wire);            // one wire message
function sendMany(bytes32 room, bytes packed);      // packed = (uint16be length ‖ wire) repeated, 1 to 16 messages
event Wire(bytes32 indexed room, bytes wire);       // one per wire message, in order
```

- `room` is the §3.5 room id as 32 bytes and `wire` is the raw §3.5 wire message (not base64), 1 to 16,448 bytes; the contract refuses anything else. `sendMany` lets a party post several messages to one room in one transaction (for example `ready` with the first frame), paying the per-transaction cost once. The event carries no sender: frames authenticate themselves (§3.4).
- To receive, a party queries the `Wire` logs of its inbound room and processes them in `(blockNumber, logIndex)` order. Reads MUST use explicit numeric block ranges, never a tag; the end of the range is the head read under TAP-20 §3.2 (the lowest head among at least `quorum` answers), optionally `confirmations` blocks further back. A reader with no saved position starts 600 blocks behind the head (the reference: `lookback`, about 5 minutes of BSC), so that frames the peer posted while it was starting up are not skipped.
- **One honest node is enough, and agreement MUST NOT be required.** Frames authenticate themselves (§3.4), so a reader queries as many nodes as it likes, each on its own: a node that refuses a range as too wide gets it split into smaller ranges (the reference halves it, down to 40 blocks), and an answer holding more logs than a node returns at once, or than the reader accepts, gets that stretch split down to a single block, read if need be through the block's receipts, since anyone can fill a block with frames. Nodes that serve receipts but refuse `eth_getLogs` (the BSC dataseed nodes do both, recorded 2026-09-26) read such blocks too, so a stuffed block rests on every node that has its receipts. A node that can read such a block neither way (its receipts refused) leaves it to the nodes that can; a frame they all omit there shows only as a gap in the session (§3.4), and the reference reader warns once for each such block. A node that has not served for a while (the reference: 20 polls) is no longer waited for, so a dead node cannot hold the reader for ever; the reader says so, once, naming the block from which it passes blocks without that node. A reorg deeper than the confirmations that moves a frame below the cursor is caught only by the overlap re-read; if every node that serves logs lets that block slide out of its history first, the frame is lost without a gap report — a case BSC's fast finality makes remote. A range is complete once at least one node has answered all of it, and the result is the **union** of the answers, keyed on (block number, log index, data), with removed logs dropped. A dishonest node can only add frames that fail to authenticate, or omit frames, which another node supplies and which §3.4 reports as a gap. Requiring the nodes to agree would instead stop the channel whenever one node lags, prunes, or refuses `eth_getLogs` — the failure mode this rule exists to avoid. (The §3.2 unanimity rule protects reads a client must trust, such as a key or a manifest; a frame is not one of them.)
- Reading a range twice (a reorg, a restart from an older block) is harmless: §3.4 refuses every frame already accepted. Anyone who has seen a room id on chain can post to it; such frames fail to decode or to authenticate and change nothing.
- **Confirmations and overlap.** A reader SHOULD stay at least 2 blocks behind the head (about 1 s on BSC). On every poll it MUST re-read at least the 16 blocks below its cursor, and it MUST do the same when resuming from a saved cursor, so that a transaction a shallow reorg moved into an already-read block is not lost. A log already handed over, identified by (block hash, or block number when absent; log index; transaction hash; data), SHOULD NOT be handed over again. A reorg deeper than the overlap may lose a frame, and the channel reports it as a gap (§3.4).
- **Everything but the content is public for ever:** the room id, the posting address, the time and the size of every frame. A party SHOULD post from a key used for nothing else, and should assume the funding of that key is public too. Latency is the block time; every message costs gas, so small frames are RECOMMENDED.
- **Log retention.** A reader needs nodes that serve `eth_getLogs` with enough history to cover the time it may be offline, and nodes that do not archive differ widely in how far back they serve logs. Measured on BSC, as examples only: `rpc-bsc.48.club` (48 Club) and `1rpc.io/bnb` (1RPC) served logs at least 500,000 blocks back (≈ 2.6 days at 0.45 s a block) on 2026-09-27, when the reference reader read a real frame 73,700 blocks back through them, and 1RPC accepts at most 50 blocks per request; `bsc-rpc.publicnode.com` served only about 5,000 to 10,000 blocks depending on the backend (≈ 40–75 min, measured 2026-09-24/25, older ranges refused with HTTP 403 and −32602 "Archive requests require a personal token") and timed out on every request on 2026-09-27; the `bsc-dataseed` nodes refuse `eth_getLogs` entirely but serve block receipts (recorded 2026-09-26). The reference SDK exports its measured set as `BUS_RPC_URLS`. A party offline for longer than its nodes' window cannot catch up from the chain alone; it needs an archive node or a relay.
- **Reading history.** A reader SHOULD learn how far back each node serves logs (probing when a node refuses as too old a block it was believed to serve is enough) and SHOULD warn the application once when its `lookback` or a saved cursor reaches further back than any node serves: frames posted in that gap cannot be read from those nodes. A client in several rooms on one bus MAY read them with one `eth_getLogs` per node per poll, giving the room topic as an OR-array; the range, confirmation and overlap rules above apply unchanged. (Reference: `busTransport({ warn })`, `oldestServed`, `busReader`, and the node set `BUS_RPC_URLS`. The reference makes one such call per node for each chunk of the range, 1,000 blocks by default, plus those that splitting a refused or over-full range adds.)
- **Hold, never skip.** A reader MUST NOT move its cursor past a block unless some node returned that block's logs, or every configured node refused it with an explicit, permanent answer that was known before the current poll and that the node gives again in the current poll (the reference accepts only two: from a node that has served no logs in the last 20 polls, or never, a statement that it does not support the method or an exact "limit exceeded", said for at least 5 minutes, since an archive node rate limited at start-up may use the same generic words; or a "too old" refusal below a floor it confirmed by probing in an earlier poll). Any other failure (a timeout, an HTTP error, a rate limit, an unfamiliar error message, running out of the per-poll time budget) MUST hold the cursor so the next poll reads the range again. A block some node answered is still not passed while a node that served logs lately has neither answered it nor refused it as too old in this poll: a fast node answering nothing must not outrun a slow honest one. Logs a node returned during a held poll are kept for the next one, per room, so a history window that slides meanwhile cannot take them away: a held cursor recovers, a skipped block is lost for ever. A reader SHOULD warn after many consecutive holds, whatever caused them, naming the range.
- The contract has no owner, no fee, no storage and no upgrade path; any deployment of the same interface works, and an invite names the one to use (`bus`, §3.2).

## 4. Rationale

- **Our own channel keys, not the TapeSend key.** The first version reused the X25519 key TapeSend publishes, for zero registration. But that key is derived from a wallet signature over text stating it should be signed only on the TapeSend site, so every third-party app implementing this TAP would have been teaching users to ignore that warning -- the habit phishing relies on. A holder-authorised record (§3.1) costs one `putFile` per container, keeps the same property (a circuit that changes hands drops its identity by itself), and supports contract holders through EIP-1271. TapeSend keys remain a fallback for the official client.
- **Triple Diffie-Hellman, not a signature.** X25519 cannot sign, and adding a signing key would mean a second key per container. `DH(eA,SB) ‖ DH(sA,EB) ‖ DH(eA,EB)` authenticates both sides (each static key participates), gives forward secrecy (ephemerals are erased) and resists key-compromise impersonation (a stolen `sA` does not let anyone pose as B to A). It is the core of Signal's X3DH without prekeys, and of Noise's KK-style patterns.
- **Invites to an inbox room, TapeSend when they must last; frames off chain by default, on chain when needed.** An invite normally goes to the peer's inbox room on a relay or ChannelBus its record lists: no holder transaction, and only the room and the size are visible. TapeSend remains the durable fallback, for a peer offline longer than relays and nodes keep data. Only the invite is durable: frames have no durable path (relay rooms live minutes, and public nodes serve logs for a window that ranges from about 5,000 blocks, roughly 40 minutes on BSC, to a few hundred thousand, §3.7) and there is no acknowledgement or retransmission in this TAP, so an application that needs every message to arrive SHOULD add its own acknowledgements on top of the channel, and a conversation both parties may leave for hours is a series of channels, not one. Frames normally travel through relays, which are fast, cost nothing per frame and keep no permanent public record. A relay, however, needs someone to run it and can be switched off. §3.7 therefore lets the chain itself carry frames as an optional transport with no operator at all: at BSC gas prices a frame costs a fraction of a cent, and the price is the permanent public metadata listed there, which a party accepts by choosing it. Authentication comes from the key schedule, not from the channel a message travelled on, so the security argument is the same on every transport, and a replayed or forged invite produces a handshake that simply fails.
- **Everything in the transcript.** Both endpoints, both static and both ephemeral keys, `cid`, `exp` and a hash of the entire invite are hashed into the HKDF salt. Omitting any one of them enables unknown-key-share or identity-misbinding attacks, in which the keys agree while the parties disagree about who they are talking to.
- **Counter nonces, strict ordering, reported gaps.** Keys are unique per channel and direction, so a counter nonce is safe and removes any dependence on randomness per frame (the WireGuard construction). Strict monotonicity kills replay and reordering; allowing gaps keeps a lossy transport usable while making every loss visible.
- **The relay is a TapeAPI service.** Posting and polling map onto ordinary TAP-21 methods, so a relay inherits TAP-20 identity, TAP-21 signed answers, TAP-22 metering and every rate limit and hosting option a provider already has. It is also the first TapeAPI service anyone needs.
- **Long-poll, not a socket.** A long-poll is an ordinary HTTPS request, which works through every proxy, runs on Workers, and falls under the off-chain request rules DeWEB shells already enforce. A frame reaches a waiting peer one round trip after it is posted.

## 5. Backwards Compatibility

Adds a TapeSend content `kind`; TAP-10 clients that do not implement this TAP display it as unsupported and are otherwise unaffected. Adds nothing to TAP-20, TAP-21 or TAP-22: a relay is an ordinary service.

## 6. Test Vectors

## 8. Security Considerations

- **Metadata.** An invite posted to an inbox room shows its room (which identifies B), its size and its time to the relay or, on a ChannelBus, to everyone for ever; an invite sent by TapeSend makes its sender, recipient, time and length public on chain (TAP-10). After that, a relay sees room names, frame sizes, timing and the IP addresses of whoever posts and polls; it does not see identities or content. A direct WebRTC connection reveals each party's IP address to the other. Parties who must hide their addresses from each other SHOULD stay on a relay.
- **Static key compromise.** A stolen static key lets the thief open new channels as that container until the holder removes or replaces the channel record (§3.1), or the record expires. The `issued` floor (§3.1) protects a client that has seen the replacement; a client that never has can still be shown the old record until it expires, so holders SHOULD keep `expires` short (RECOMMENDED: at most 90 days) and renew. It does not expose past channels (forward secrecy) and does not let the thief impersonate others to the victim (KCI resistance).
- **Inbox rooms are public.** Anyone can derive a container's inbox room and post to it; junk fails to open and changes nothing, and relays bound what a room stores (§3.5). On a ChannelBus, the fact that B received something at time T is public for ever.
- **Stale invites.** An invite can be replayed until `exp`. The result is a handshake that cannot complete, because only the real initiator holds `eA`; responders SHOULD still remember accepted `cid`s until `exp` so as not to spend effort twice.
- **Denial of service.** A relay can drop everything, or report a poisoned index or oversized answers, which amounts to the same; the parties see gaps or silence and SHOULD fall back to another relay from the invite. A priced `relaySend` makes flooding a room cost the flooder; a free relay relies on rate limiting (TAP-21 §3.4).
- **Truncation.** There is no authenticated end of channel, so a relay can cut off the tail of a conversation without detection. Applications that need to know a conversation ended SHOULD send an explicit final message and treat silence as loss.
- **Relay correlation.** A relay trivially links the two rooms of one channel (they are used together), and relays that share logs can link one another. Channel room names still reveal no identity (inbox rooms name their container by design).
- **Constant time in JavaScript.** The reference implementation compares tags in a data-independent loop, but a JIT gives no guarantee. Each forged tag needs a fresh handshake, so this is acceptable for 256-bit tags.
- **No channel-level non-repudiation.** Frames are authenticated with symmetric keys, so either party could have produced any frame. Applications that need to prove to a third party what the other side said MUST have that side sign the relevant messages with a key a third party can verify; this TAP deliberately does not.
- **Compromised endpoints.** Nothing here protects a party from a peer who records or leaks what it receives, and nothing prevents two peers from colluding over another channel.

# TAP-26：Tape Channel：容器之间的实时私密通道（中文译文）

> 以英文为准。章节编号与上半部分一一对应。

> **占位编号。** TAP-26 是在 [TapeKit issue #8](https://github.com/TapeOutProtocol/TapeKit/issues/8) 中提议的占位编号。TapeKit 目前还没有编号提案流程（对 TapeOut 本身的修改遵循 TapeKit `SPEC.md` §15），因此维护者可能另行分配编号，或把本文档移入其它流程；见 [TAP-1](TAP-1.md)。

> **实现状态（2026-09-27）：** 运行中：ChannelBus 已部署于 BNB Chain `0x486110c35d9b90a9d6D85c8063A065f9e7b6b707`（代码与参考构建逐字节一致）；免费公共中继运行于 `relay.tapeapi.fun`（`12.1013.tape`，源码 `examples/cloudflare-worker/relay-worker.js`）；SDK 实现了经中继与 ChannelBus 的通道，并导出一组实测的总线节点 `BUS_RPC_URLS`（§3.7）。未经第三方审计。

## 1. 摘要

Tape Channel 是两个 TapeOut 容器之间一条端到端加密、双向认证、有序的消息流。它由一份邀请建立（投进对方在中继或 ChannelBus 上的收件房间，此为默认；或作为 TapeSend 消息发送，此为持久备用），之后可以走任何传输层：本身就是 TapeAPI 服务的中继（默认：快、每帧免费、不留永久记录）、浏览器之间的直连，或在不需要或没有中继时经由 ChannelBus 走链上（§3.7）。每一方的身份是电路持有人授权、发布在容器自己 DeWEB 站点里的通道密钥，因此通道不需要新合约、不需要可信服务器，也不需要在别的网站的文字上签名。

## 2. 动机

DeWEB 承载网站，TapeSend 承载人与人之间的消息，但 TapeSend 的每条消息都写上链：要花 gas、要等一个区块，谁和谁说话是公开的。生态里没有任何东西支持那种每秒要来回很多次、又不能被旁听的对话，这也是为什么到目前为止所有 TapeOut 游戏都是单机的。带隐藏手牌的牌类游戏、一场谈判、实时协作的文档、向单个客户端流式推送结果的服务，都需要一条私密、快速、单条消息几乎零成本、同时又绑定在生态已信任的链上身份上的通道。

TAP-26 只提供这条通道，别的刻意不管。它不涉及游戏、状态机或结算，这些由应用在上面构建。

## 3. 规范

### 3.1 身份与密钥

- 每一方是一个 TapeSend 端点：`uint32(0) ‖ uint64(chainId) ‖ container`（32 字节，与 TAP-10 完全一致）。
- **通道身份（默认）。** 容器在本 TAP 中的身份是一对由应用生成并保存的密钥：X25519 密钥（握手的**长期密钥**）与 Ed25519 密钥（供 TAP-27 群消息使用）。电路持有人在 TAP-20 的 EIP-712 域（`name "TapeAPI"`、`version "1"`、`chainId`、`verifyingContract` = DeWebHub）中对 `ChannelKeys(address container,bytes32 x25519,bytes32 ed25519,bytes32 inbox,uint64 issued,uint64 expires)` 签名授权，并在容器的 DeWEB 站点注册表键 `.well-known/tape-channel.json` 处发布记录（格式见英文部分）。签名结构中的 `inbox` 是记录中 `inbox` 规范化后的哈希 `keccak256(UTF-8(canonicalJSON({ "relays": [ { "url", "container" } ], "bus"? })))`：`relays` 总是存在（每项只保留 `url` 与 `container`；缺省时为 `[]`），`bus` 仅在存在时出现。因此持有人的签名覆盖了邀请发往何处，能写站点的人无法把邀请引走。`sig` 对 ECDSA 持有人为 65 字节（`r ‖ s ‖ v`），对合约持有人（EIP-1271）至多 1,024 字节。类型名与 TAP-20 的 `Delegation` 不同，服务委托因此绝不能被当作通道授权重放。从不把钱包签名变成密钥：持有人签的是写明授权内容的结构化数据，也不会要求持有人签署为其它网站准备的文字。
- **读取方式。** 已知容器时，调用它的 ERC-6551 `token()` 得到 `(chainId, circuits, tokenId)`，`chainId` MUST 等于正在读取的链，`DeWebHub.accountOf(circuits, tokenId)` MUST 等于该容器，且处理器工厂对 `isCPU(circuits)` MUST 回答 `true`（与 TAP-20 §3.6 相同的检查：容器自己的 `token()` 只是声称，而 `accountOf` 对任何 ERC-721、包括仿冒的，都能推导出账户）。用 `SiteRegistry.read` 读取记录，并按 TAP-20 §3.2 校验清单的方式对照 `fileInfo` 校验字节（至多 4,096 字节）。记录 MUST 能按 TAP-21 §3.3 的严格规则解析；`container` 与 `chainId` MUST 一致；`x25519` MUST 通过下述检查；`ed25519` MUST 通过下述 Ed25519 检查；`issued` MUST 为整数，至多超前读取方时钟 300 秒，且小于 `expires`；`expires` MUST 晚于现在且至多提前 366 天（此处为 MUST，而 TAP-20 §3.4 为 SHOULD：通道身份必须会失效）；`inbox` 各项 MUST 满足 §3.2 第 1 步。最后，签名 MUST 恢复为此刻读取的 `ownerOf(circuits, tokenId)`；若该持有人是合约，MUST 按 EIP-1271 认可该签名：`isValidSignature(digest, sig)` MUST 返回完整的 32 字节字 `0x1626ba7e` 后接零。电路转手后通道身份因此自动失效。所有读取均按 TAP-20 §3.2 的多节点一致规则进行。持有人删除该文件即可提前撤回身份。客户端 MUST 按容器记住它接受过的记录中最高的 `issued`，并 MUST 拒绝 `issued` 更低的记录（SHOULD 持久化这一下限）：持有人替换记录时，旧签名并不会失效；没有这一下限，任何能写站点的人都能把被替换的记录（连同泄露的密钥）放回去。持有人替换记录时，新记录的 `issued` MUST 更大。
- **TapeSend 密钥（备用）。** 一方 MAY 改用 TAP-10 §4 由持有人钱包派生、发布在 DeWebHub 上的 X25519 密钥认证，用 `DeWebHub.keyFor(circuits, tokenId)` 读取（返回的 `container` 与 `endpoint` MUST 一致，`usable` MUST 为 true，`suite` MUST 为 1）。该派生要求持有人签署一段写明"只应在 TapeSend 网站签署"的文字，因此官方 TapeSend 客户端以外的实现 SHOULD NOT 要求用户这样做。2026-09-22 对容器 `0x86DDaEF00401E3F10418398D67D7189fc458eA95` 调用 `keyFor` 返回了一把可用的套件 1 密钥（原始响应见 `sdk/test/fixtures/mainnet-4246-tapesend-key.json`）。
- 邀请写明双方所用的密钥种类（`keys`：`"tape-channel/v1"` 或 `"tapesend/v1"`，§3.2），握手记录绑定该字段。客户端 MUST NOT 从本 TAP 的任何消息中取得对方的长期公钥。
- 客户端收到的每一把公钥（长期或临时）MUST 为 32 字节、最高位为 0、规范编码（`u < 2^255 − 19`），且 MUST NOT 产生全零的 X25519 共享密钥（TAP-10 §4.4）。任一条不满足 MUST 放弃握手。
- 每把 Ed25519 公钥 MUST 能解码为 Ed25519 上的点，且 MUST NOT 是小阶点：小阶公钥能让一个签名对任何消息都验证通过。

### 3.2 握手

三条消息。A 为发起方，B 为响应方。角色由谁发出邀请决定。

1. **邀请**（A → B）。A 随机生成 16 字节通道号 `cid` 与一对临时 X25519 密钥 `(eA, EA)`，构造上文英文部分所示的邀请 JSON。`from` 与 `keys` 为 REQUIRED。`from` 指明发起方，`keys` 指明双方使用的长期密钥种类（§3.1）；B MUST 按 `keys` 所指的种类、依 `from` 查出 A 的长期公钥，且 MUST 拒绝 `from` 与其所查公钥不属同一方的邀请。邀请中的任何内容都不被信任为身份依据：伪造的 `from` 或 `keys` 会改变 `inviteHash`，握手随之失败（§3.3）。

   **投递。** 邀请可经以下任一路径到达 B；两者都安全，因为认证邀请的是握手而不是路径：

   - **收件房间（默认）。** 每个容器在其记录 `inbox` 所列的任一中继（§3.5）或 ChannelBus（§3.7）上有一个收件房间 `SHA-256("TAP-26/inbox/v1" ‖ endpoint)`。A 在此投递线路消息 `0x03 ‖ E ‖ N ‖ C`（构造见英文部分：以 B 的长期公钥做 X25519、HKDF-SHA256 派生密钥、XChaCha20-Poly1305 加密邀请的规范 JSON），其中 HKDF 的 `info` 与 AAD 里的 `room` 是房间号的 32 个原始字节。整条线路消息至多 16,448 字节。线路类型 `0x03` 承载任意 `v` 为 1、`kind` 为字符串的严格 JSON 对象，接收方按 `kind` 分派：TAP-26 邀请（`tape.channel/invite`）与 TAP-27 入群邀请（`tape.group/invite`）共用它，二者不会被混淆。任何人都能投递，无需持有人交易。外界只看得到房间（它指向 B）与大小。
   - **TapeSend（持久备用）。** A 的持有人发送一条内容为该邀请、密封给 B 长期公钥的 TapeSend 消息（TAP-10 §5.3）。它能送达离线时间超过中继或节点数据保留期的对方，代价是一笔持有人交易。B MUST 核对 TapeSend 的 `from` 等于 `invite.from`。

   不实现本 TAP 的 TAP-10 客户端会把该内容解码为不支持的类型（TAP-10 §6），且 MUST NOT 据此行事；无需修改 TAP-10。

   `exp` MUST 不晚于发送时刻之后 3600 秒（RECOMMENDED 600）。`relays` 列出 A 将要监听的至多 4 个 TapeAPI 中继服务（§3.5）；每个 `url` MUST 是不超过 512 字符的 `https` URL（与任何 TAP-20 端点一样，仅开发时的回环地址允许 `http`），`container` MUST 是中继的 TAP-20 身份（20 字节十六进制地址）。客户端按该容器解析中继（TAP-20 §3.6），从而得知它的签名者、价格与当前端点；只有 URL 则什么都得不到，因此省略容器的邀请无法被使用。`bus` 为 OPTIONAL：A 同时在其上监听的 ChannelBus 地址（§3.7）。邀请 SHOULD 至少列出一个中继或一个总线；两者皆无的邀请只能在带外作答。`webrtc` 为 OPTIONAL（§3.6）；若提供，MUST 具有规范形式（TAP-21 §3.3），因为整个邀请都会哈希进握手记录（§3.3）。`cid` 以 32 个小写十六进制字符发出；接收方 MUST 按字节而非字符串比较通道号。

2. **接受**（B → A，发到邀请所列中继或 ChannelBus 上 A 的入站房间）。对邀请而言 `exp` 不含端点：除非 `now < exp ≤ now + 3600`，B MUST 拒绝；B MUST 按 §3.1 校验 `EA`、按第 1 步校验 `relays`，且 SHOULD 拒绝已经接受过的 `cid`（在 `exp` 之前记住已接受的通道号是应用的职责；参考 SDK 接受调用方传入的集合）。B 生成 `(eB, EB)`，按 §3.3 派生密钥，发送 `{ "t": "accept", "cid", "e": EB, "confirm": confirmResponder }`。密钥派生完毕后 B MUST 销毁 `eB`。

3. **就绪**（A → B，经同样的传输层）。A 在发送任何内容之前 MUST 以常数时间核对 `accept.confirm`，且只在 `now < exp` 时接受 `accept`。核对不通过的 `accept` MUST 被丢弃，MUST NOT 建立会话；A 继续等待有效的 `accept` 直到 `exp`（任何能读 A 中继房间的人都能投递一条伪造的 `accept`，把它当作致命错误等于把"一键掐断"交给每个中继观察者）。收到有效 `accept` 后，A 发送 `{ "t": "ready", "cid", "confirm": confirmInitiator }` 并 MUST 销毁 `eA`；同一握手的第二条 `accept` MUST NOT 再次完成它。B MUST 以常数时间核对 `ready.confirm`，MUST 拒绝 `now < exp` 不成立时到达的 `ready`（与邀请相同，不含端点），在核对通过前 MUST NOT 接受任何入站帧。

A 的待完成握手状态（`eA` 及由其派生的一切）MUST NOT 被持久化或复制：同一握手完成两次会派生出相同的密钥、`seq` 从 0 重来，从而重用 nonce。状态丢失的握手以新邀请重新开始。

B MAY 在发出 `accept` 后立即发送帧：只有同时持有 `sA` 与 `eA` 的一方读得了它们。

### 3.3 密钥调度

公式见英文部分（握手记录末尾包含 `inviteHash`，即整个邀请内容规范 JSON 的 SHA-256）。`kAB` 保护 A 到 B 的帧，`kBA` 保护 B 到 A 的帧，两者 MUST NOT 用于另一个方向。实现 SHOULD 在算出确认标签后销毁 `ikm`、`okm`、`cA`、`cB` 与三次 DH 输出。

`inviteHash` 绑定了邀请携带的一切，包括 `relays` 与 `webrtc`，因此在传递中被改动的邀请（换掉中继列表、改了 `exp`）得到的确认标签无法通过核对。

### 3.4 帧

- 每个方向各自维护 `seq`，从 0 开始、每帧加一。发送方 MUST NOT 重复使用 `seq`，且 MUST 在 `seq` 达到 2^32 之前另开新通道。
- 每帧明文 MUST NOT 超过 16,384 字节。
- 接收方 MUST 拒绝 `seq` 不大于该方向已接受最大 `seq` 的帧（重放、重复或乱序），MUST 拒绝认证失败的帧。接收方 MUST 接受空洞并 SHOULD 把空洞大小报告给应用：传输层可能丢帧，能否容忍丢失由应用决定。
- 把明文解码为文本的接收方 MUST 在推进已接受最大 `seq` 之前解码，并 MUST 拒绝不是合法 UTF-8 的已认证帧、且不消耗它。
- 通道的机密性、完整性与顺序 MUST NOT 依赖传输层。

### 3.5 中继配置

中继是一个 TAP-20/21 服务，其清单列出三个方法：`relaySend`（运营方定价，MAY 为 0，按 TAP-22 每次调用计费；参数 `{ room, frame }`，返回 `{ i, epoch }`）、`relayHandshake`（价格 MUST 为 0；参数 `{ room, frame }`，返回 `{ i, epoch }`）与 `relayRecv`（免费；参数 `{ room, after, waitMs, epoch? }`，返回 `{ frames: [{ i, frame }], next, epoch }`），详见英文部分表格。

- `room` 为 `SHA-256("TAP-26/room/v1" ‖ cid ‖ dir)` 的小写十六进制，`dir = 0x00` 表示发**给**发起方，`0x01` 表示发**给**响应方。只有读过邀请的一方知道 `cid`，所以通道房间名是猜不到的凭据，且不透露身份。收件房间（§3.2）则不然：任何人都能推导出某个容器的收件房间并往里投递。
- `frame` 是一条**线路消息**的标准（带填充）base64：`0x01 ‖ UTF-8 JSON`（`accept` 或 `ready`）、`0x02 ‖ 帧`（§3.4），或投进收件房间的 `0x03 ‖ 密封邀请`（§3.2）。中继限制单帧大小（参考中继为 22,000 个 base64 字符，足以容纳最大的线路消息，16,448 字节）。
- `i` 是中继在房间内自己的序号，严格递增。`relayRecv` 返回 `i > after` 的已存帧（客户端第一次的 `after` 为 −1）；若没有，MAY 将请求挂起至多 `waitMs`，一有新帧立即返回。中继把 `waitMs` 限制在自身的响应期限之下（参考中继为 20,000 毫秒，低于参考服务器 25,000 毫秒的处理超时），否则满时长的轮询会得到 `INTERNAL` 而不是空结果。
- **单次回答 MUST 放得进 TAP-21 的 1 MiB 上限。** 中继按字节预算（参考中继为 512 KiB）返回放得下的若干帧，至少一帧，并用 `next` 指明从哪继续，客户端立即再轮询一次。若中继一次返回全部积压，房间里攒够大帧之后每次轮询都会失败：游标永不前进，通道彻底死掉——而任何知道房间号的人都能免费触发这一点。
- **收费中继 MUST 通过 `relayHandshake` 免费承载握手。** 其 `frame` 很小（参考中继为至多 2,048 个 base64 字符），且 MUST 解码为 `0x01` 后接一个 `t` 为 `accept` 或 `ready` 的 JSON 对象；其它一律被中继拒绝。中继 MAY 拒绝每个房间超过 N 条的此类消息（参考中继为 8）。免费通道创建的房间有独立的数量上限（参考实现：1,000）和更短的寿命（参考实现：10 分钟），直到有付费的 `relaySend` 接管该房间，因此免费通道无法塞满收费中继的房间表。响应方必须先回应邀请，那时它还没有任何理由已向该中继充值，而 `accept` 正是告诉发起方通道已建立的消息；若要为它付费，就得在邀请有效期内完成三笔链上交易。
- `next` 是下一次调用应作为 `after` 传入的值：最后返回的 `i`；未返回任何帧时即原 `after`；房间的 `epoch` 已变且未返回任何帧时为 −1。
- **纪元。** 中继 MUST 在房间创建时为其生成随机 `epoch`（RECOMMENDED 8 字节十六进制；MUST 匹配 `^[0-9a-f]{1,32}$`），并由每个方法返回（房间不存在时 `relayRecv` 返回 `null`）。重建的房间（中继重启、房间过期、新的 Durable Object）序号从头开始，因此客户端 MUST 随 `after` 一并发送上次看到的 `epoch`（房间当时不存在或客户端尚未轮询过它则为 `null`；中继 MUST 接受它，它与任何纪元都不同）；中继的 `epoch` 不同时 MUST 按 `after` 为 −1 作答，客户端 MUST 重置游标。中继 SHOULD 同时接受不带 `epoch` 字段的请求（2026-09-27 之前的参考客户端在尚未见到纪元时就这样发送），并按原样的 `after` 作答。否则记住序号 N 的客户端会悄悄跳过新房间的前 N+1 帧。
- **房间。** 只有投递（`relaySend` 或 `relayHandshake`）才创建房间；对不存在房间的 `relayRecv` 只等待，不创建也不钉住房间，中继 SHOULD 单独限制挂起请求的数量。中继 SHOULD 限制每个房间的帧数、房间寿命与房间总数，并 SHOULD 让空闲房间至少保留 600 秒（RECOMMENDED 的邀请寿命），使发起方短暂离线时投递的 `accept` 仍在；MAY 丢弃房间里最旧的帧（接收方会看到空洞）。中继 MUST NOT 为腾出空间而清理尚未过期的房间；满了就拒绝新房间（`INTERNAL`，或边缘返回 HTTP 503），因为清理活跃房间会让任何人冲掉别的通道尚未取走的帧。
- **多个传输。** 发起方从发出邀请起直到 `exp`，MUST 在邀请所列的每个中继和每个 ChannelBus 上监听 `accept`。响应方 SHOULD 按邀请所列顺序（先中继、后总线）把 `accept` 发到第一个可达的传输上，MAY 发到全部传输。接收方 MUST 把经多个传输到达的相同线路消息视为一条。`ready` 及之后的帧 SHOULD 走 `accept` 到达的那个传输。参考实现的 `fanIn` 把多个传输合为一个。
- **邀请与纪元消息单独保存。** 中继 MUST 把线路类型 `0x03`（密封邀请）与 `0x04`（群纪元消息）放在帧（`0x02`、`0x05`）无法挤掉的独立上限之内（参考实现：每房间 64 条，先丢最旧的），使一场帧洪水（在免费中继上不花一分钱）无法在对端读取之前冲掉其收件房间或群的当前纪元。同一房间内 `relayRecv` MUST 仍按投递顺序、在同一序号序列下返回所有类型的消息。中继 SHOULD 按房间、按来源限制 `0x03` 与 `0x04` 的投递数（参考实现：每 10 分钟 8 条，付费调用以消费者为键，否则以调用方地址为键；无法识别的调用方对整个房间算作同一个来源），超出者作为调用方错误（`BAD_REQUEST`）拒绝。
- 客户端 MUST 逐帧独立解码：格式错误的帧被报告并跳过，绝不能让它连带丢弃其后的帧。
- 中继在内容、顺序、完整性上 MUST NOT 被信任：这三者客户端全靠 §3.4。
- 由于每个 `relayRecv` 的回答都是 TAP-21 信封，中继关于"已送达/未送达"的说法是签了名的。

### 3.6 直连传输（OPTIONAL）

双方 MAY 把通道迁到 WebRTC 数据通道上。SDP offer MAY 放在邀请里（`webrtc.sdp`），answer 放在 `accept` 里。直连上传的是同样的帧、同样的密钥、同样的 `seq` 计数器，因此通道可以在中继与直连之间双向切换而无需重新协商，接收方对收到的任何东西一律按 §3.4 处理。

DeWEB 页面究竟能否建立 WebRTC 连接，是本 TAP 之外由外壳决定的事（TapeKit SPEC §7 管辖链下请求，目前未涉及 WebRTC）。所有实现 MUST 支持中继传输；直连只是优化。

### 3.7 链上传输（OPTIONAL）

链本身就可以承载通道，不需要中继、也没有运营者。**ChannelBus** 是具有如下接口的合约（接口见英文部分，参考实现 `contracts/src/ChannelBus.sol`；BNB Chain 上已部署于 `0x486110c35d9b90a9d6D85c8063A065f9e7b6b707`，其代码与参考构建逐字节一致；任何具有此接口的合约同样可用）：`send(bytes32 room, bytes wire)` 发送一条消息；`sendMany(bytes32 room, bytes packed)` 一笔交易发送 1 到 16 条，`packed` 为重复的 `uint16 大端长度 ‖ 消息`；每条消息发出一个事件 `Wire(bytes32 indexed room, bytes wire)`，顺序与发送顺序一致。

- `room` 为 §3.5 的房间号（32 字节），`wire` 为 §3.5 的原始线路消息（不做 base64），长度 1 到 16,448 字节，其它一律被合约拒绝。`sendMany` 让一方在一笔交易里向同一房间发送多条消息（例如 `ready` 与第一帧），每笔交易的基础费用只付一次。事件不含发送者：帧自带认证（§3.4）。
- 接收方查询自己入站房间的 `Wire` 日志，按 `(blockNumber, logIndex)` 顺序处理。读取 MUST 使用显式的数字区块区间，绝不用标签；区间终点是按 TAP-20 §3.2 读取的链头（至少 `quorum` 个答案中最低的链头），可再往回退 `confirmations` 个区块。没有保存读取位置的读取方从链头之前 600 个区块开始（参考实现：`lookback`，约合 BSC 的 5 分钟），使对端在本方启动期间发出的帧不被跳过。
- **一个诚实节点就够，MUST NOT 要求节点一致。** 帧自带认证（§3.4），因此读取方可以向任意多个节点查询，每个节点各自读取：节点嫌区间太宽而拒绝时，把区间拆小再读（参考实现对半拆分，最小 40 个区块）；一个回答里的日志多于节点单次返回的、或多于读取方接受的，就把那一段拆到单个区块，必要时读该区块的回执，因为任何人都能用帧塞满一个区块。提供回执但拒绝 `eth_getLogs` 的节点（BSC 的 dataseed 节点正是如此，2026-09-26 录制）也来读这样的区块，于是塞满的区块由所有有回执的节点作证。某个节点两种方式都读不了这样的区块（回执被拒）时，就交给能读的节点；它们都漏掉的帧只会在会话里表现为空洞（§3.4），参考实现对每个这样的区块警告一次。一段时间没有提供读取的节点（参考实现：20 次轮询）不再被等待，这样死节点不会让读取方永远停住；读取方会说一次，并给出从哪个区块起不等它就越过。比确认数更深、把帧挪到游标之下的重组只能靠重叠区的重读发现；如果每个提供日志的节点都先让那个区块滑出了历史窗口，这个帧会丢失而不报告空洞——BSC 的快速最终性使这种情况极少出现。只要有一个节点完整回答了某区间，该区间即读完，结果取各答案的**并集**，以（区块号、日志序号、数据）为键去重，并丢弃已移除（removed）的日志。不诚实的节点只能塞进认证不通过的帧，或漏掉某些帧——后者由其它节点补上，§3.4 会把缺口报告出来。反过来要求节点一致，只会在任一节点落后、裁剪历史或拒绝 `eth_getLogs` 时停掉通道，而这正是本条要避免的失效方式。（§3.2 的一致规则保护的是客户端必须信任的读取，例如密钥或清单；帧不属于此类。）
- 同一区间读两次（重组、从更早的区块重启）无害：§3.4 会拒绝所有已接受的帧。在链上看到房间号的任何人都能往里发送；这样的帧解码或认证失败，不改变任何状态。
- **确认数与重叠。** 读取方 SHOULD 至少落后链头 2 个区块（BSC 上约 1 秒）。每次轮询 MUST 至少重读游标之下的 16 个区块，从保存的游标恢复时也 MUST 如此，这样被浅重组挪进已读区块的交易不会丢失。已交出的日志以（区块哈希，缺失时用区块号；日志序号；交易哈希；数据）标识，SHOULD NOT 再次交出。比重叠更深的重组可能丢帧，通道会把它报告为空洞（§3.4）。
- **除内容外一切永久公开：** 房间号、发送地址、每帧的时间与大小。各方 SHOULD 使用专用的发送密钥，并假定该密钥的资金来源同样公开。延迟为出块时间；每条消息都付 gas，RECOMMENDED 使用小帧。
- **日志保留期。** 读取方需要提供 `eth_getLogs` 且历史足以覆盖其可能离线时长的节点，而非归档节点能提供多久以前的日志差别很大。BSC 上的实测，仅作示例：`rpc-bsc.48.club`（48 Club）与 `1rpc.io/bnb`（1RPC）在 2026-09-27 提供了至少 500,000 个区块以前的日志（按每块 0.45 秒约 2.6 天），参考读取器当天经它们读回了 73,700 个区块以前的真实帧，另外 1RPC 每次请求至多接受 50 个区块；`bsc-rpc.publicnode.com` 视后端只提供约 5,000 到 10,000 个区块（约 40 到 75 分钟，2026-09-24/25 实测，更早的区间以 HTTP 403 与 −32602 "Archive requests require a personal token" 拒绝），并在 2026-09-27 对每个请求都超时；`bsc-dataseed` 节点完全拒绝 `eth_getLogs`，但提供区块回执（2026-09-26 录制）。参考 SDK 把实测的节点集导出为 `BUS_RPC_URLS`。离线时间超过节点保留窗口的一方无法仅靠链追上进度，需要归档节点或中继。
- **读取历史。** 读取方 SHOULD 了解每个节点能提供多久以前的日志（节点以"太旧"拒绝一个本以为它能提供的区块时探测即可），并且当其 `lookback` 或保存的游标早于任何节点所能提供的范围时，SHOULD 向应用发出一次警告：发布在这段空缺里的帧无法从这些节点读到。在同一总线上加入多个房间的客户端 MAY 每次轮询对每个节点只发一次 `eth_getLogs`，把房间 topic 写成"或"数组；上述区间、确认数与重叠规则不变。（参考实现：`busTransport({ warn })`、`oldestServed`、`busReader`，以及节点集 `BUS_RPC_URLS`。参考实现对区间的每一段（默认 1,000 个区块）向每个节点发一次这样的调用，再加上拆分被拒或过满的区间所增加的调用。）
- **宁可停住，绝不跳过。** 除非有节点返回了某区块的日志，或者每个配置的节点都以明确且永久的回答拒绝了它（该回答在本次轮询之前就已得知，且节点在本次轮询中再次给出；参考实现只认两种：最近 20 次轮询内（或从来）没有提供过日志的节点，持续至少 5 分钟表示不支持该方法、或原话回答 "limit exceeded"（启动时被限流的归档节点也可能用同样的通用措辞）；低于在更早轮询中经探测确认的下限的"太旧"），读取方 MUST NOT 把游标移过该区块。其它任何失败（超时、HTTP 错误、限流、不认识的错误信息、用完本次轮询的时间预算）MUST 让游标停住，由下一次轮询重读该区间。有节点答过的区块，只要最近提供过日志的某个节点在本次轮询中既没答它、也没以"太旧"拒绝它，仍不越过：回答「空」的快节点不能跑在慢的诚实节点前面。停住那次轮询中节点返回的日志按房间留给下一次轮询，期间滑动的历史窗口拿不走它们：停住的游标能恢复，跳过的区块永远丢失。连续停住多次后，不论原因，读取方 SHOULD 发出警告并写明区间。
- 该合约没有所有者、没有费用、没有存储、不可升级；同一接口的任何部署都可以用，由邀请指定使用哪一个（`bus`，§3.2）。

## 4. 原理

- **用自己的通道密钥，而不是 TapeSend 密钥。** 第一版为了零登记沿用了 TapeSend 发布的 X25519 密钥。但那把密钥由钱包对一段写明"只应在 TapeSend 网站签署"的文字签名派生而来，于是每个实现本 TAP 的第三方应用都会在训练用户无视这条警告——这正是钓鱼所依赖的习惯。持有人授权的记录（§3.1）每个容器只多一笔 `putFile`，保持同样的性质（电路转手后身份自动失效），并通过 EIP-1271 支持合约持有人。TapeSend 密钥作为官方客户端的备用方案保留。
- **三重 DH，而非签名。** X25519 不能签名，再加一把签名密钥就意味着每个容器两把钥匙。`DH(eA,SB) ‖ DH(sA,EB) ‖ DH(eA,EB)` 同时给出双向认证（每把长期密钥都参与）、前向保密（临时密钥被销毁）与抗密钥泄露冒充（被盗的 `sA` 不能让任何人对 A 冒充 B），是去掉预密钥的 Signal X3DH 核心，也是 Noise KK 类模式的核心。
- **邀请投进收件房间，需要持久时用 TapeSend；帧默认在链下，需要时上链。** 邀请通常投进对方记录所列中继或 ChannelBus 上的收件房间：无需持有人交易，外界只看得到房间与大小。TapeSend 仍是持久备用，用于离线时间超过中继与节点数据保留期的对方。持久的只有邀请：帧没有持久路径（中继房间只存几分钟，公共节点的日志保留窗口从约 5,000 个区块（在 BSC 上约 40 分钟）到几十万个区块不等，见 §3.7），本 TAP 也没有确认与重传，因此需要每条消息都送达的应用 SHOULD 在通道之上自行加确认，双方可能离开数小时的对话应当是一系列通道，而不是一条。帧通常经由中继传递：快、每帧零成本、不留永久的公开记录。但中继要有人运行，也可能被关掉。因此 §3.7 允许由链本身作为可选传输来承载帧，完全没有运营者：按 BSC 的 gas 价格每帧不到一分钱，代价是该节列出的永久公开元数据，由选择它的一方自行接受。认证来自密钥调度而不是消息经过的渠道，所以在每种传输上的安全论证都相同，被重放或伪造的邀请只会得到一次必然失败的握手。
- **所有东西进握手记录。** 双方端点、双方长期与临时公钥、`cid`、`exp` 以及整个邀请的哈希全部哈希进 HKDF 的盐。漏掉任何一项都会给未知密钥共享或身份错绑攻击留出空间：密钥一致，双方对"在和谁通话"的认识却不一致。
- **计数器 nonce、严格顺序、报告空洞。** 密钥按通道和方向唯一，因此计数器 nonce 是安全的，也不再依赖每帧的随机数（WireGuard 的构造）。严格单调杜绝重放与乱序；允许空洞让有损传输仍然可用，同时让每一次丢失都可见。
- **中继本身是 TapeAPI 服务。** 发送与轮询对应普通的 TAP-21 方法，中继因此继承 TAP-20 身份、TAP-21 签名回答、TAP-22 计费，以及提供者已有的全部限流与托管选项。它也是人人都用得上的第一个 TapeAPI 服务。
- **长轮询，而非 socket。** 长轮询就是普通 HTTPS 请求，能穿过任何代理、能跑在 Workers 上，也落在 DeWEB 外壳已经执行的链下请求规则之内。一帧在发出后一个往返就能到达正在等待的对端。

## 5. 向后兼容

新增一个 TapeSend 内容 `kind`；不实现本 TAP 的 TAP-10 客户端会将其显示为不支持，其余不受影响。不向 TAP-20、TAP-21、TAP-22 添加任何内容：中继只是一个普通服务。

## 6. 测试向量

`spec/vectors/tap-26-channel.json` 固定了双方的长期与临时私钥，并给出每一个中间值：双方端点、邀请哈希、三次 DH 输出、握手记录、`kAB`、`kBA`、`cA`、`cB`、两个确认标签、两个房间名，以及四帧（含一个空帧和一个含非 ASCII 文本的帧）。`spec/vectors/tap-26-identity.json` 固定持有人私钥与通道密钥，给出收件地址哈希、`ChannelKeys` 摘要及持有人对它的签名、一个收件房间，以及一份带临时密钥与随机数的密封邀请。`spec/vectors/verify.py` 用照各自规范（RFC 7748、RFC 5869、RFC 8439 与 XChaCha 草案）在 Python 中独立实现的 Keccak-256、EIP-712、X25519、HKDF-SHA256、ChaCha20-Poly1305 与 XChaCha20-Poly1305 重新计算全部数值。

## 8. 安全考量

- **元数据。** 投进收件房间的邀请，其房间（指向 B）、大小与时间对中继可见，在 ChannelBus 上则对所有人永久可见；经 TapeSend 发送的邀请，其发件人、收件人、时间与长度在链上公开（TAP-10）。此后，中继能看到房间名、帧大小、时间以及收发方的 IP 地址，看不到身份和内容。WebRTC 直连会把每一方的 IP 暴露给对方。需要对彼此隐藏地址的双方 SHOULD 始终走中继。
- **长期密钥泄露。** 被盗的长期密钥可以让窃贼以该容器身份开启新通道，直到持有人删除或替换通道记录（§3.1），或记录到期。`issued` 下限（§3.1）保护见过新记录的客户端；从未见过的客户端在旧记录到期前仍可能被出示旧记录，因此持有人 SHOULD 让 `expires` 保持较短（RECOMMENDED：至多 90 天）并按期续签。它不会暴露过去的通道（前向保密），也不能让窃贼对受害者冒充他人（抗 KCI）。
- **收件房间是公开的。** 任何人都能推导出某个容器的收件房间并往里投递；垃圾消息打不开，不改变任何状态，中继也限制每个房间的存储（§3.5）。在 ChannelBus 上，"B 在时间 T 收到了东西"这一事实永久公开。
- **过期邀请。** 邀请在 `exp` 之前可以被重放，结果只是一次无法完成的握手，因为只有真正的发起方持有 `eA`；响应方仍 SHOULD 在 `exp` 之前记住已接受的 `cid`，以免重复耗费资源。
- **拒绝服务。** 中继可以丢弃一切，或报出被污染的序号、超大的回答，效果相同；双方会看到空洞或沉默，SHOULD 改用邀请里的另一个中继。收费的 `relaySend` 让刷房间的人自己付钱；免费中继依靠限流（TAP-21 §3.4）。
- **截断。** 没有经过认证的通道结束标记，中继可以截掉对话的尾部而不被察觉。需要知道对话已结束的应用 SHOULD 发送明确的结束消息，并把沉默视为丢失。
- **中继关联。** 中继能轻易把同一通道的两个房间关联起来（它们总是一起使用），共享日志的多个中继也能相互关联。通道房间名仍然不透露身份（收件房间则按设计指向其容器）。
- **JavaScript 中的常数时间。** 参考实现用与数据无关的循环比较标签，但 JIT 不作保证。每伪造一个标签都需要一次新握手，对 256 位标签而言可以接受。
- **通道层没有不可否认性。** 帧用对称密钥认证，任何一方都可能产生任意一帧。需要向第三方证明对方说过什么的应用，MUST 让对方用第三方可验证的密钥为相关消息签名；本 TAP 刻意不提供这一点。
- **端点被攻破。** 这里没有任何东西能防止对方记录或泄露其收到的内容，也无法阻止两个对端经由别的渠道串通。
