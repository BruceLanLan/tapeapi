# TapeAPI 规划复盘与 v0.2 方向

日期：2026-09-20。对照新目标重新审视 v0.1。

## 新目标（Bruce 的表述，整理后）
1. TapeAPI 首先是**一个标准**，目的是让 Web2 企业、加密企业（DeFi、游戏、公链）能用最简单的方式接入 TapeOut 生态，或把 TapeOut 生态的东西接出去。
2. 费用由开发者自己决定，我们不强制收；给出一个建议的抽成标准，愿意给的按最低比例给，作为开发维护费。参考 Blonskr 的 DeWEB 与 TapeSend 均零协议费。
3. 在此基础上思考跨链、跨链兑换、流动性。TapeAPI 只传数据，不是桥，但要能让流动性经由它流动。
4. 以 TAP 标准形式投稿到 TapeOut 生态。
5. 官网 + 中英 README + 接入示例，部署到 tapeout.work 的一个页面。

## v0.1 哪里对、哪里要改

| v0.1 设计 | 复盘结论 | v0.2 动作 |
|---|---|---|
| 服务身份 = 电路容器，清单存链上 | 对，这是与 DeWEB/TapeSend 对齐的根基，且每个 API 消耗一个电路，创始人最在意 | 不变 |
| 签名响应 + 会话密钥凭证，一次调用零 gas | 对，Web2 企业接入的前提是"调用和普通 HTTPS 一样快" | 不变 |
| Escrow 由我们设 2% 手续费 | **错**，与目标 2 和生态先例冲突，也让"标准"变"产品" | 改为提供者自设的 `contributionBps`，默认 0，建议 1%，见 FEES.md |
| 别名登记费归我们 | 部分错。防抢注是必要的，但价值应流向协议 | 登记条件改为"容器已激活"（激活费本来就付给协议），登记费默认 0 |
| 只考虑 BSC 单链 | 不够。TAP-10 端点已含 chainId，生态本身是多链设计 | 支付与身份多链化，见 CROSSCHAIN.md |
| 服务 = 链下算力 + 链上身份 | 不够"划时代"。TapeOut 独有的是**电路可在链上 eval** | 新增"电路验证方法"，见 CROSSCHAIN.md §3 |
| 示例只有一个 reader | 不够。目标用户是四类企业，每类要一个 20 行能跑的示例 | 见 examples/ 目录规划 |
| 面向对象是 DeWEB 站点开发者 | 太窄。真正的增量用户在生态外 | 官网与 README 面向"把现有 API 接进 TapeOut"的人 |

## 四类目标用户与各自的"最简接入"

| 用户 | 他已有什么 | 接入动作（目标：30 分钟） | 他得到什么 |
|---|---|---|---|
| Web2 企业（SaaS、数据商、AI 商） | 一个 REST API 和一个 API Key 体系 | 用 `@tapeapi/server` 包一层适配器：把现有 REST 端点映射为 method，签名与计费自动完成；铸一个电路当身份 | 免开户的按次付费客户、BEM 结算、身份不可被平台封禁 |
| DeFi 协议 | 合约 + 子图 + 前端 | 发布一个 price/quote/route 服务；或者反过来在前端用 SDK 调别人的服务 | 一个不需要自建预言机委员会的可验证数据源 |
| 游戏 | 游戏服务器 + 排行榜 + 存档 | 把排行榜、存档、匹配封成服务；玩家存档存到玩家自己的容器 | 存档跟随玩家 NFT，可跨游戏读取 |
| 公链 / L2 | RPC 节点 | 发布"Attested Read"服务：对本链任意状态给出签名、区块锚定的读取结果 | 让 TapeOut 生态的应用无桥读取该链，导入用户 |

## v0.2 交付清单
- 合约：Escrow 费率模型重做；Directory 增加激活门槛
- SDK/Server：跟随合约改动；增加"多提供者仲裁"调用模式（`quorum: 2`）
- 示例：web2-adapter、defi-price-oracle、gaming-leaderboard、chain-attested-read，每个含中英 README 与一条 curl
- 规范：TAP-22 改费率条款；新增 TAP-23（Attested Read）、TAP-24（Intent RFQ）、TAP-25（Circuit-Verified Methods）草案
- 官网：`site/` 静态站，纯相对路径，可直接作为 DeWEB 站点或放到 tapeout.work 子路径
- README 中英重写

## 关于 TAP 编号
TapeKit 仓库内部只用过 `TAP-10`（消息层）。不存在正式编号表。我们在 TAP-1 里提议 10–19 为消息、20–29 为服务，维护者最终分配。投稿时编号写"建议 TAP-20"，由他们定。
