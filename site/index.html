回执长什么样

What a receipt looks like

每个回答，附一张谁都能核验的回执

Every answer carries a receipt anyone can check

AI 用量回执的结构取自 TAPI-21 规范，数值为示例。

The structure of an AI usage receipt comes from the TAPI-21 spec; the values are examples.

x-tapeapi-receipt
{ "id": "chatcmpl-v1", "ok": true,
  "container": "0x…",                             1
  "ts": 1790000000,
  "method": "openai_chat",
  "params": { "path": "/v1/chat/completions",
              "requestSha256": "<64 hex>" },      2
  "result": {
    "model": "gpt-x",                             5
    "usage": { "prompt_tokens": 1200, "completion_tokens": 300,
               "total_tokens": 1500, "cache_read_tokens": 1000,
               "reasoning_tokens": 100 },         4
    "responseSha256": "<64 hex>",                 3
    "stream": false, "complete": true, "status": 200,
    "prices": [ { "currency": "USDT", "amount": "0.00357500" },
                { "currency": "BEM",  "amount": "0.03375000" } ],  4
    "modelMatchedBy": "response" },
  "sig": "0x…" }                                  1
  1. container 与 sig：谁签的。签名能恢复出签名者，它必须是电路持有人在链上委托的密钥。
  2. container and sig: who signed. The signature recovers the signer, which must be a key the circuit's holder delegated on chain.
  3. params.requestSha256：答的是哪个请求。你发出的字节的哈希，由你的 SDK 对照。
  4. params.requestSha256: which request. The hash of the bytes you sent, compared by your SDK.
  5. result.responseSha256：回了哪些字节。
  6. result.responseSha256: which bytes came back.
  7. usage 与 prices：声称的用量，和按链上价目表算出的金额；任何人都能重算。价目表只是公开声明，不经结算，用户照旧向服务方付款。
  8. usage and prices: the claimed usage, and the amount from the on-chain price table; anyone can recompute it. The price table is a public statement, not settled: users pay the provider as before.
  9. model：只是上游报的名字。回执不证明实际跑的是哪个模型。
  10. model: only the name the upstream reported. A receipt does not prove which model actually ran.

回执不证明实际跑的是哪个模型。服务方可以把便宜模型的回答标成贵的。签名带来的是可追责：回执无法抵赖，任何人发测试请求、公开结果，都会留下证据。

A receipt does not prove which model actually ran. A provider could label a cheaper model's answer as a dearer one. What the signature adds is accountability: a receipt cannot be disowned, so anyone sending test prompts and publishing the results leaves evidence.

NEW IN 3.0

三样新东西，都在你自己的机器上完成

Three new things, all done on your own machine

  • Agent 护照：tapeapi passport、@tapeapi/passport。在同一个钉住的区块上读链，两家以上运营方一致才下结论：这个 ERC-8004 身份和这枚 TapeOut 电路，是不是同一个钱包持有；读不一致就说「不知道」。
  • Agent Passport: tapeapi passport, @tapeapi/passport. It reads the chain at one pinned block and concludes only when two or more operators agree: whether one wallet holds this ERC-8004 identity and this TapeOut circuit. When the reads disagree it says "unknown".
  • 策略电路：@tapeapi/policy-circuit。花钱的规则写成小电路，对方自己重跑，拿不准就拒绝。
  • Policy circuits: @tapeapi/policy-circuit. A spending rule is written as a small circuit that the other side re-runs; when unsure, it denies.
  • 花费清单与本地预算：tapeapi receipts statement。按服务、模型、天汇总，并在调用发出之前拦住超额。
  • Spend statement and local budget: tapeapi receipts statement. It sums spend by service, model and day, and stops an over-limit call before it is sent.

限制，如实说

The limits, plainly

  • 新增的两个包是 0.1.0、实验性，不在兼容承诺之内。
  • The two new packages are 0.1.0, experimental, and outside the compatibility promise.
  • 相关的 TAP 草案（#83、#84）已提交（评审中），未合并；提交不等于被采纳。
  • The related TAP drafts (#83, #84) are submitted (in review), not merged; submitting is not adoption.
  • 主网上目前还没有已知的 CONFIRMED 护照。
  • No CONFIRMED passport is known on mainnet yet.
  • 策略电路只约束去检查它的一方。
  • A policy circuit binds only those who check it.
  • 回执只证明签名方说了什么。
  • A receipt proves only what its signer said.
  • 付费托管合约未经审计、未部署，今天不收任何费用。
  • The paid-call escrow is not audited and not deployed; nothing is charged today.
  • 3.0 有五项破坏性修改，每一项（除 Node.js 22 下限）都有保留 2.x 行为的选项。
  • 3.0 has five breaking changes; each but the Node.js 22 floor has an option that keeps the 2.x behaviour.
DEFAULT SINCE 2.0

标准即默认。不传选项，SDK 就按 TapeOut 官方 TAP 解析服务：每次解析钉一个区块，链 ID 与持有人要所有节点一致，名字未开通或未付费就得到一个明确的状态，而不是悄悄解析成功。TAP-11 与 TAP-13 由我们起草，已合并为 Draft（合并不等于被采纳）。要 1.x 的行为，传 conform: false。

Standards by default. Pass no options and the SDK resolves a service as TapeOut's official TAPs say: one pinned block, all nodes agreeing on chain and owner, and a named status for a name not opened or not paid up. TAP-11 and TAP-13 to TAP-18, drafts we wrote, are merged as Drafts (a merge is not adoption). For 1.x: conform: false.

同一版首次公开三项实验性功能——有界代理、美元报价、容器间评价。它们依赖的托管合约未经审计、未部署，主网不可用，今天只在本地链与测试中可以验证，也不收任何费用。

The same release first makes public three experimental features: bounded agents, US-dollar prices and reviews between containers. The escrow they rely on is not audited and not deployed, so they do not work on mainnet; today they are checked on local chains and in tests only, and nothing is charged.

Install from the GitHub release

The packages are not on npm yet; install them from the GitHub release into an empty directory. Node.js 22 or later is required.

shell
npm install \

A · curl向公共服务要 BNB 价格。curl 只显示签名信封，不做任何核对；验签用 SDK 或调试台。Ask the public service for the BNB price. curl shows the signed envelope and checks nothing; the SDK or the playground verifies it.

shell
curl -s https://api.tapeapi.fun/tapeapi/v1/bnbUsd -H 'content-type: application/json' -d '{"id":"1","params":{}}'

B · SDK存为 try.mjs，在装好 SDK 的目录里运行 node try.mjs：SDK 从链上解析服务、验签，验签成功才返回结果。Save this as try.mjs and run node try.mjs in the directory where the SDK is installed: the SDK resolves the service from the chain and verifies the answer before it returns.

try.mjs
import { createTapeAPI, rpcUrlsFor } from '@tapeapi/sdk'
const api = createTapeAPI({ rpcUrls: rpcUrlsFor(56) })      // 3 家运营方的节点nodes of 3 operators
const service = await api.resolve('11.1013.tape')            // 按官方 TAP 解析resolved as the official TAPs say
const { result, verified } = await api.call(service, 'bnbUsd', {})
console.log(result.bnbUsd, verified)                         // 验签成功才为 truetrue only after the signature checked out

状态

Status

3.x 遵循语义化版本：按 3.0 文档写的代码在所有 3.x 版本里继续工作（标注为实验性的接口和 0.x 包除外）；3.0.0 发布后 2.x 继续获得 6 个月的安全修复，1.x 到 2027-04-12。没有第三方审计；安全说明见参考页。

3.x follows semantic versioning: code written to the 3.0 docs keeps working in every 3.x release (interfaces marked experimental and the 0.x packages excepted); 2.x receives security fixes for 6 months after 3.0.0, and 1.x until 2027-04-12. No third-party audit; the security note is on the reference page.
